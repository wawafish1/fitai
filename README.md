# FitAI 轻盈计划

一个移动端优先的 90 天减脂记录网站。它把个人资料、训练消耗、拍照记餐、三大营养素、体重/腰围趋势和 10～15 天阶段复盘放在同一条简单流程里。

当前版本：`v1.0.0`

线上地址：[https://app.fitai.website](https://app.fitai.website)

> 本项目以用户指定的谭成义约 47 分钟完整视频中“根据身体反馈分阶段调整碳水”的思路为产品依据，但不是谭成义的官方产品，也不构成医疗或营养处方。

## 为什么做这个项目

常见饮食记录工具需要逐项搜索食物、选择份量，步骤多，长期坚持困难。FitAI 的核心优势是“先拍照，再核对”：用户拍下一餐或上传相册照片，AI 先拆分食物并估算份量，用户只需要逐项确认和修改，系统再自动汇总热量、碳水、蛋白质和脂肪。

这套流程刻意保留人工确认。照片无法可靠判断所有食材、份量和烹调用油，AI 结果被视为可编辑的初步估算，而不是精确测量。

## v1.0.0 功能

### 邮箱验证码登录

- 任意有效邮箱可直接获取验证码，首次验证自动创建账号。
- 登录状态默认保持 30 天，服务端使用 `HttpOnly`、`SameSite=Lax` Cookie。
- 同一邮箱 60 秒发送冷却、每小时最多 10 次；同一 IP 每小时最多 20 次。
- 账号之间的数据、餐食照片和 AI 使用次数相互隔离。

### 个人资料与消耗估算

- 支持生理性别、年龄、身高、体重、腰围和体质倾向。
- 支持轻/中/高训练强度，力量和有氧可选常用时长或填写自定义分钟数。
- 支持“练几休几”，自动展示训练日、休息日和完整周期的日均消耗。
- 今日页面可以手动切换训练日或休息日，消耗展示为“静态 + 运动”。

### AI 拍照记餐

- 手机直接拍照或从相册选择图片。
- 上传前在浏览器压缩至最长边不超过 2048px、JPEG 质量 0.9，以兼顾清晰度和速度。
- 服务端以高细节模式识别普通餐食，并拆成每一种食物、估算克数和每 100g 营养基准。
- 每项食物都能单独核对、修改或删除；修改后由程序重新计算整餐结果，避免模型汇总误差。
- 支持包装食品营养成分表，区分每 100g、每 100ml 和每份，支持 kJ 换算 kcal。
- 看不清的字段或无法确定的实际食用量不会自动填成 0，而是要求用户补充。
- 每个账号每天可成功识别 10 张，北京时间零点重置；失败请求会返还次数。
- 已保存餐食可在今日记录中打开只读详情，查看照片、食物说明和三大营养素。

### 身体趋势与阶段复盘

- 记录体重、腰围、饥饿感、干净碳水渴望、精神、训练和睡眠恢复。
- 每日状态可修改或删除，删除前需要二次确认。
- 复盘周期可设为 10 天或 15 天，且至少需要 7 次本阶段状态记录。
- 调整建议同时参考体重/腰围变化和主观状态，不做机械的每日降碳。
- 完成复盘后保存当时的系数和变化原因，并开启下一阶段。

## 计算方式

### 三大营养素目标

目标克数取最近一次体重记录（没有记录时使用资料体重）乘以当前系数：

- 碳水：默认 `3.0 g/kg`，可在 `2.0～5.0 g/kg` 内调整；起步提示为 `2.5～3.5 g/kg`。
- 蛋白质：默认 `1.6 g/kg`，范围 `1.2～2.0 g/kg`。
- 脂肪：默认 `0.76 g/kg`，范围 `0.6～0.8 g/kg`。
- 目标热量：`碳水克数 × 4 + 蛋白质克数 × 4 + 脂肪克数 × 9`。

### 每日消耗

- 静息能量使用 Mifflin–St Jeor 公式，男性常数为 `+5`，女性为 `-161`。
- 静态消耗约为 `静息能量 × 1.2`。
- 运动消耗按净 MET 估算：`(MET - 1) × 3.5 × 体重(kg) ÷ 200 × 分钟数`。
- 力量训练轻/中/高分别采用 3.5/5/6 MET；有氧采用 4/6/8 MET。
- 周期日均消耗按设置的训练天数和休息天数加权平均。

所有消耗与营养结果都用于趋势参考，不等同于代谢实验或称量结果。

## 技术架构

| 层级 | 技术与职责 |
| --- | --- |
| 前端 | React 19、TypeScript、Vite、移动端自适应界面 |
| 服务端 | Node.js 22、Express 5、同源 API |
| 数据 | SQLite 保存账号与记录，服务器磁盘保存压缩餐食照片 |
| 登录 | 腾讯云 SES 邮箱验证码 |
| AI | OpenAI 兼容的视觉对话接口，密钥仅保存在服务端 |
| 部署 | Docker Compose + Caddy HTTPS 反向代理 |
| 测试 | Node Test、Playwright、GitHub Actions |

数据流简化如下：

```text
手机浏览器
  ├─ 邮箱验证码 ──> FitAI 服务端 ──> 腾讯云 SES
  ├─ 资料/餐食/趋势 ──> SQLite
  └─ 餐食照片 ──> 服务端压缩文件存储 + AI 视觉接口
                         └─ 返回逐项食物估算，用户确认后保存
```

## 本地运行

要求：Node.js 22+、npm。

```bash
npm ci
cp .env.example .env
npm run build
npm start
```

默认访问 `http://localhost:3000`。本地若要完整测试登录、同步和 AI，需要在 `.env` 中配置腾讯云 SES 与 AI 接口；仅开发前端时可运行：

```bash
npm run dev
```

关键环境变量：

| 变量 | 用途 |
| --- | --- |
| `APP_ORIGIN` | 生产网站来源，例如 `https://app.fitai.website` |
| `SESSION_SECRET` | 会话和验证码摘要密钥，生产环境必填且应为长随机值 |
| `SESSION_DAYS` | 登录保持天数，默认 30 |
| `DAILY_ANALYSIS_LIMIT` | 每账号每日成功识别次数，默认 10 |
| `TENCENT_SES_*` | 腾讯云 SES 地域、发信地址、模板和受限 CAM 子用户密钥 |
| `AI_API_URL` | OpenAI 兼容的聊天完成接口 |
| `AI_MODEL` | 支持图片输入的模型名 |
| `AI_API_KEY` | AI 服务端密钥，严禁使用 `VITE_` 前缀 |
| `DATA_DIR` | SQLite 与照片目录，容器内默认 `/app/data` |

完整字段和服务器步骤见 [部署文档](docs/DEPLOYMENT.md)。任何真实密钥都不要提交到 Git。

## 测试

```bash

```

测试覆盖：

## Docker 部署

最短流程：

```bash
cp .env.example .env
docker network create writing-assistant-proxy
docker compose up -d --build
```

然后将 [Caddyfile](Caddyfile) 加入同一代理网络。生产部署、DNS、HTTPS、备份、升级和回滚步骤见 [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)。

## 安全与隐私

- `.env`、SQLite 数据库、照片目录、测试账号和本地验收产物均被 Git 忽略。
- 腾讯云密钥和 AI Token 只由 Node 服务端读取，不进入浏览器构建产物。
- 写接口校验来源，验证码和 AI 请求均有限流；验证码最多尝试 5 次。
- 生产响应启用 CSP、HSTS、禁止页面嵌入、MIME 嗅探防护和最小权限策略。
- 餐食照片属于敏感个人数据。生产环境应定期备份、限制服务器访问，并制定删除和保留策略。

安全注意事项和密钥轮换建议见 [SECURITY.md](SECURITY.md)。

## 已知限制与下一步

v1.0.0 已可供小规模实际使用，但还有这些值得继续改进：

1. AI 只能估算照片中可见内容；最好增加“同一餐多角度照片”和常吃食物模板。
2. 目前没有“忘记/更换邮箱”、账号注销和一键导出数据，正式开放注册前应补齐。
3. 当前是单机 SQLite + 本地磁盘照片，用户量增大后应迁移到托管数据库和对象存储。
4. 可增加备份自动化、监控、异常告警、邮件投递状态和管理员用量面板。
5. 可增加 PWA 安装、离线记录后自动同步、微信内浏览器专项兼容测试。
6. 可为常见餐食建立个人历史，让用户复用上次确认值，降低每天核对成本。
7. 需要更多真实设备、屏幕阅读器和弱网测试；当前自动化测试不能代表完整 WCAG 合规。

版本变化见 [CHANGELOG.md](CHANGELOG.md)。
